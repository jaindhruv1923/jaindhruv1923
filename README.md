## 🔍 How I Work

> Every project README, dashboard, and case study I ship is written against the actual notebook or dataset that produced the numbers in it — not the other way around.

This isn't a slogan, it's a habit I can point to with receipts. A few things I've caught and fixed in my own work before publishing:

- A dashboard metric that quietly disagreed with the notebook that was supposed to be its source of truth.
- A "raw row count" that turned out to be a file's *line count*, not its actual record count — off by a meaningful margin.
- A cluster count in a write-up that was off by one from what the trained model had actually produced.
- Early drafts of Profitara's marketing copy claimed USD figures, an XGBoost model, and Prophet forecasting — none of which matched the actual build (INR data, Random Forest, Holt-Winters). I went back and scrubbed every fabricated claim, keeping only numbers I could trace to the notebook: CLV R² = 0.930, churn AUC = 0.91, revenue in ₹66.95L.

If a number is in one of my READMEs, I can show you the cell or query it came from.

### 📊 Profitara — Retail BI & Customer Analytics Platform

<p align="center">
  <img src="https://raw.githubusercontent.com/jaindhruv1923/Project-Profitara-Retail-BI-Pipeline/main/02_health_scorecard.png" width="48%"/>
  <img src="https://raw.githubusercontent.com/jaindhruv1923/Project-Profitara-Retail-BI-Pipeline/main/04_churn_distribution.png" width="48%"/>
</p>

[![Repo](https://img.shields.io/badge/Repo-View_on_GitHub-181717?style=for-the-badge&logo=github)](https://github.com/jaindhruv1923/Project-Profitara-Retail-BI-Pipeline)
[![Live](https://img.shields.io/badge/Live-Streamlit_Dashboard-FF4B4B?style=for-the-badge&logo=streamlit&logoColor=white)](https://project-profitara-retail-bi-pipeline.streamlit.app/)

End-to-end retail analytics pipeline on a 10,000-row India quick-commerce transaction dataset — 4,918 orders across 1,448 customers, ₹66.95L total revenue, 4.15% margin. Built to answer one question a retail ops team actually asks: *which customers are worth protecting, and which ones are already gone?*

- 🌲 **CLV prediction** — Random Forest regressor, R² = 0.930
- 📉 **Churn modeling** — Logistic Regression classifier, AUC 0.91, 361 at-risk customers flagged for intervention
- 🧩 **RFM segmentation → K-Means clustering** — 119 customers identified as "Champions"
- 🔗 **Market basket analysis** — Apriori algorithm surfaced 52 cross-sell rules
- 🌲 **Anomaly detection** — Isolation Forest flagging irregular transaction patterns
- 📈 **Demand forecasting** — Holt-Winters exponential smoothing
- 📊 13-page interactive Streamlit dashboard, a matching Power BI build, and a PostgreSQL/DuckDB SQL layer underneath both

<details>
<summary><b>🔧 Technical deep-dive</b></summary>
<br/>

- Deployed on Streamlit Community Cloud — resolved real deployment blockers along the way: `config.toml` placement issues, a pandas 3.x deprecation break, and chart-rendering bugs that only showed up post-deploy.
- Every headline metric on the dashboard is cross-checked against the model notebook that generated it — this project is the one where I caught and removed fabricated USD/XGBoost/Prophet claims from early drafts (see *How I Work* above).
- Segmentation logic: RFM scoring feeds K-Means, not the reverse — segments are behavior-derived, not manually bucketed.

</details>

`Python` `scikit-learn` `Streamlit` `PostgreSQL` `DuckDB` `Power BI`

### 🕵️ Naukri Saaf — Ghost Job Listing Detection Platform

<p align="center">
  <img src="https://raw.githubusercontent.com/jaindhruv1923/Project-Naukri-Saaf-Job-Listings-Analysis/main/media4.png" width="48%"/>
  <img src="https://raw.githubusercontent.com/jaindhruv1923/Project-Naukri-Saaf-Job-Listings-Analysis/main/Screenshot_2026-07-21_142519.png" width="48%"/>
</p>

[![Repo](https://img.shields.io/badge/Repo-View_on_GitHub-181717?style=for-the-badge&logo=github)](https://github.com/jaindhruv1923/Project-Naukri-Saaf-Job-Listings-Analysis)
[![Live](https://img.shields.io/badge/Live-Streamlit_Dashboard-FF4B4B?style=for-the-badge&logo=streamlit&logoColor=white)](https://project-naukri-saaf-job-listings-analysis.streamlit.app/)

ML pipeline built on ~3,000 real listings scraped from LinkedIn, Indeed, and Glassdoor (cleaned down to 2,851), engineering 73 features per listing to flag likely "ghost" postings — job ads that are live but not really hiring. The model flags 29.3% of listings as high-risk.

- 🤖 **5 classifiers benchmarked** — best performer: Gradient Boosting, AUC 0.716
- 🔬 **SHAP explainability** attached to every individual listing's score, not just the model globally
- 🧑‍💼 **5 employer behavioral clusters** derived from posting patterns, including a "High-Risk Ghost Poster" cluster covering 1,361 employers
- 🧩 **Chrome extension** — scores listings entirely client-side, zero network calls, so nothing about what you're browsing ever leaves your machine
- 📊 7-tab Streamlit dashboard + an 8-page Power BI dashboard (1280×720 canvas, custom DAX measures driving the insight text boxes) + a full SQL pipeline + an Excel workbook

<details>
<summary><b>🔧 Technical deep-dive</b></summary>
<br/>

- Labels came from a weak-supervision scheme (no ground-truth "ghost job" labels exist publicly), which meant validating the labeling logic itself before trusting anything downstream — including catching a data-leakage issue in an earlier synthetic version of this dataset where the label was near-deterministically encoded in a feature.
- Power BI build involved a genuinely obscure fix: a `.pbix` file is a ZIP archive under the hood. Editing the report JSON directly required dropping the `SecurityBindings` file and cloning textbox schemas from a working file rather than hand-constructing them from guessed properties — undocumented, found by trial and error.
- Chrome extension architecture deliberately avoids any server round-trip for scoring, so it works offline once loaded.

</details>

`Python` `scikit-learn` `SQL` `Chrome Extension` `Power BI` `SHAP`
